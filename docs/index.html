01. Install

One command

$ brew install phranck/grat/grat

Release binaries are published for macOS and Linux on Intel and ARM.

$ man grat

grat help prints a short overview of every command there is. For a full description, the package ships a complete set of man pages. man grat, or man 1 grat, describes every command along with how grat works. man grat.config, or man 7 grat.config, describes every option the configuration file takes.

  1. grat discoverReads your project and writes a declarative grat.config from what it finds. Give it a path and it searches below there, so a whole folder of projects is set up in one pass.
  2. grat startStarts every service and waits until each one answers.
  3. grat statusShows what runs, on which port, under which PID, and what is public.
02. What it runs

Any command that stays in the foreground

grat is tied to no language, framework or package manager. It starts your command through /bin/sh from the project root, in a session of its own, and hands it the port in PORT. Whether that command is Node, PHP, Python, Swift or Go makes no difference to grat.

What a service has to do. Stay in the foreground, because a command that puts itself in the background leaves nothing for grat to watch. Serve its port from a process that grat started, or from one of its children. Answer its health path with a status in the 200s.

A worker does none of that. It has no port, and it counts as ready for as long as its process lives.

Where that boundary sits. grat follows the port back to the process holding it and up its chain of parents. If that chain does not lead to the command grat started, the service never becomes ready, and grat says so rather than pretending.

That rules out anything whose port is held by a separate daemon. A container started through Docker is the common case: the listener belongs to Docker, not to your command.

Most of that config writes itself. grat discover reads the project and proposes what it finds. Angular, Astro, Next.js, Nuxt, React Router, SvelteKit and Vite are recognised on the frontend, Django, Laravel, Rails and FastAPI on the backend, along with Go modules and Swift packages using Vapor. Every command it writes carries the port and the host, because a development server that binds every interface is on the network by accident.

Sometimes it asks you instead, and that is the point. Express, Fastify, NestJS and Go read no port of their own and have no flag for one, so the port sits in the line of your code that starts the server. grat looks there for process.env.PORT or os.Getenv("PORT"). If it finds it, you get a command. If it does not, grat names the file and the reason rather than guessing, because a guessed port produces a service that runs perfectly and never reports ready. You then either read the port from the environment, or name the command once with --service name=command.

The environment is small on purpose. A command inherits ten variables, namely HOME, LANG, LC_ALL, LC_CTYPE, LOGNAME, PATH, SHELL, TERM, TMPDIR and USER, plus whatever it lists in inherit_env. Everything else you happen to have exported stays out, so a service behaves the same however your shell is set up.

03. Services

Ready means ready, not started

A process that has been launched is not a service that answers. grat waits for a listener owned by the command it started, then for the health path to return, and only then calls it ready.

Start

Each command runs in its own process session, with the port it was given in PORT and a small, deliberate environment.

Stop

Signals reach the process group grat created, and only after the live PID, start identity and group all match what it recorded.

Logs

Output goes straight to .grat/log/, so a service keeps its log after the command that started it has exited.

05. Public access

A webhook can reach your laptop

Whether you want to show somebody on the other side of the world how your site or web app currently looks, or you need a webhook URL that reaches your local development environment, grat gives you a way to do it. Underneath, the exposing runs on Tailscale. You prepare nothing: where Tailscale is missing, grat installs it and says so as it goes. Two steps stay with you, because they cannot be taken on your behalf. The background service starts with administrator rights, so the system asks for your password, and the sign-in runs through your browser because that is where your account is.

$ grat expose backend
$ grat expose --path /api/webhooks/creem backend

Running the command is the decision, so nothing has to be prepared first. Where only a callback has business with the internet, name the path and everything else stays inside.
