# Releasing grat

A release touches two repositories and has waiting points between its steps. The order is not free, and getting it wrong is not always visible afterwards.

## Decide the number first

Read `git log --no-merges v<last>..HEAD`. A `Feat:` in there makes it a minor bump. Only `Fix:`, `Chore:`, `Docs:`, `Test:` and `Refactor:` make it a patch. Removing a command is a breaking change and belongs in the conversation before it is tagged, not in the tag.

## Write the note whilst writing the commit

The notes are built from the commit subjects, and a subject is written for
somebody who has the diff in front of them. Where the reader of a release page
would need a different sentence, put it in the commit as a `Release-note:`
trailer and that is what goes out. `scripts/release-notes.sh` explains the shape.

The grouping comes from the prefix, so a change somebody using grat would notice
is `Feat:`, `Fix:` or `Docs:`. `Chore:`, `Test:` and `Refactor:` never appear in
the notes at all, which is right for repository work and wrong for anything else.

## The order

1. **Raise the site badge in `docs/index.html`** to the version being prepared, on a `release/vX.Y.Z` branch. This is the one place the repository names a version.
2. **Run `sh scripts/gates.sh`.** Every gate, not a selection.
3. **Open the pull request, wait for all four checks, merge.**
4. **Tag and push**: `git tag -a vX.Y.Z -m "grat vX.Y.Z" && git push origin vX.Y.Z`.
5. **Wait for the Release workflow.** It builds four binaries, generates both manual pages, packages four Homebrew bottles, writes the grouped notes and publishes.
6. **Fetch the checksums** from `checksums.txt` of the new release, and the SHA256 of the source tarball.
7. **Update the tap** at `../homebrew-grat`, on its own `release/vX.Y.Z` branch: seven values in `Formula/grat.rb`, being the source URL, the source checksum, the bottle root URL and four bottle checksums. Run `ruby test/formula_binary_test.rb`.
8. **Open the tap pull request and wait for all three checks.** They install the formula for real, which is the only thing that proves the bottles are reachable and their digests right.
9. **Merge, then `brew upgrade grat`** and check `grat version`.

## The two places this goes wrong

**Merging the tap before its checks finish.** Done on 2 September 2026. The checks are the only thing that downloads each bottle and verifies its digest against the published archive, so merging early publishes a formula nobody has proven. Wait for all three.

**The badge and the tag cannot both be first.** The gate compares the badge against the newest tag, and the tag does not exist whilst the commit that raises the badge is in review. `scripts/check-docs.sh` therefore accepts a badge naming a version newer than the newest tag, and refuses one older. If that check ever fails during a release, read which direction it failed in before changing anything.

## What does not need doing

The site does not need a separate deployment. `.github/workflows/pages.yml` publishes on every push to main, and the release workflow calls it again once the release exists, so the badge names the version that was just published. It reads that version from the newest release as it builds, so what the site shows cannot name something that does not exist.

That call is a job rather than an event. A release created by the workflow is created with `GITHUB_TOKEN`, and GitHub raises no workflow run from an event a workflow's own token caused, so the `release: published` trigger fires only for a release somebody publishes by hand. The site job deploys from a tag, which the `github-pages` environment permits through a deployment policy for `v*` beside the ones for `main` and `gh-pages`. If that policy is ever removed, the release will publish and the site job will fail straight after it.

The manual pages are generated by the release workflow from the binary it just built. `Documentation.md` is generated too, and its gate runs in CI.

## Afterwards

Say what was released and what it carries, in a few sentences. The grouped notes on the release page are the detail, so do not repeat them.
